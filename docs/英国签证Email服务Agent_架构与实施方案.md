# 英国签证 Email 服务 Agent：架构设计与实施方案

版本：1.0｜设计基准日期：2026 年 11 月 14 日｜文档定位：技术负责人设计与执行交接

适用读者：产品负责人、技术负责人、签证业务专家，以及承担实现工作的开发 agents。

本文只定义产品边界、系统设计、执行约束和验收方法，不包含实现代码。本文的指标、工期与预算示例是建议目标或规划假设，不代表已经完成测试或已经取得的业务结果。

## 1. 设计结论与已确认范围

**推荐建设一个以 Email 为客户交互入口、以案件为中心、由持久化工作流控制进度、由受约束的 AI 完成理解与起草、以规则和人工审核保证放行质量的材料交付系统。**

系统的核心资产是案件事实、证据关联、路线规则和交付记录。邮件中的自然语言是服务界面，不是业务状态的唯一存储。

已确认的需求：

- 仅接入 Email，不设计 WhatsApp 接入、消息模板或渠道切换。
- 支持访客、学生、工作等多个签证类型。
- 服务像顾问一样主动推进：了解情况、索取材料、识别矛盾、解释缺口、跟进、准备最终材料。
- 交付到申请材料准备完成；本期不包含自动登录 UKVI、提交申请、付款、预约或代替申请人作法定声明。
- 本文指导后续开发 agents 执行，不在本次工作中实现系统。

为避免“多类型”被实现成“所有路线均可自动处理”，作以下产品决策：

| 范围层次 | 本方案决定 |
|---|---|
| 第一批业务路线 | Standard Visitor、Student、Skilled Worker，分别建立完整规则包与验收集 |
| 自动化覆盖 | 每条路线先覆盖经业务专家确认的标准场景，按路线单独开放自动化 |
| 复杂案件 | 未成年人、受抚养人、境内转换/续签、拒签史、复杂资金与过渡条款可进入同一系统，但由相应专业人员主导 |
| 其他工作路线 | Global Talent、Global Business Mobility 等不能套用 Skilled Worker 规则；未启用专用规则包前转人工或明确不受理 |
| 客群 | 不硬编码国籍或申请地；首批运营客群待业务确定，国籍、居住地、申请地、境内/境外均为案件条件 |
| 语言 | 默认支持中文沟通及英文沟通、英文申请文件起草；其他语言须独立评测后启用 |
| 客户界面 | 邮件即可完成主要服务；内部有审核工作台。可选安全文件传输页只承担文件传输，不构建另一套客户办理门户 |

建议架构决策：

1. 一个案件协调器负责进度，多个边界清晰的 AI 能力模块处理任务；不用自由讨论的多 agent 群作为生产主流程。
2. 使用可恢复、可等待、可审计的工作流；客户数天不回复不会导致 agent 一直运行。
3. 规则引擎判断条件与完整性，AI 解释材料与提出建议，人工处理专业判断及例外。
4. 所有关键结论追溯到具体证据、有效规则版本及审核者。
5. 先实现最小的端到端案件闭环，再增加三条路线的深度；不同时搭建大量微服务。
6. 首发所有最终材料包由有相应能力和权限的人工审核。是否允许某类案件自动放行，作为后续单独决策。

## 2. 交付结果、完成定义与商业边界

### 2.1 服务承诺应如何定义

对客户承诺：依据已确认的个人情况和适用要求，协助整理、检查和准备可用于后续申请的材料包，并明确尚待完成的动作。

不能把签证批准、使馆审理时间、文件真实有效或“绝无补件”作为系统能够保证的交付结果。识别出材料矛盾也不等于认定客户欺诈。

“像人类顾问”的具体含义是：记住已确认的信息、理解本轮回复、优先解决阻塞项、说明为什么需要材料、提醒下一步，并在超出能力边界时安排人工。向客户说明存在 AI 辅助和人工服务，不伪装成真实持牌顾问。

### 2.2 最终交付物

| 交付物 | 内容 | 验收要求 |
|---|---|---|
| 案件摘要 | 路线、申请人、申请地点、关键日期、适用规则版本 | 与客户确认及证据一致；不宣称已经递交 |
| 材料目录 | 文件名称、版本、用途、对应要求、适用申请人 | 每个目录项指向实际文件；无错人、漏页和重复旧版 |
| 支持材料 | 收到的有效版本原件扫描件或电子文件 | 保留来源；处理副本与原件分开；不篡改内容 |
| 翻译文件 | 原文、译文及所需译者确认信息 | AI 草稿与完成必要人工确认的译件有不同状态 |
| 必要的说明文件 | 有需要时起草的说明信、资金说明或其他叙述文件 | 每个关键事实有来源；不把通用 cover letter 设为所有路线必交 |
| 申请填写参考表 | 已确认字段及其来源、待申请人自行核对项 | 不是已提交的官方申请表，也不声称与未来表单字段永久一致 |
| 下一步说明 | 官方办理入口、需要客户完成的动作、时间敏感提醒 | 说明适用日期及重新检查触发条件 |

内部保留详细审查记录和证据定位；客户交付包不包含内部模型评分、他人信息和无关内部讨论。

### 2.3 三种结果必须分开

- **最终材料包**：所有适用硬性检查已完成，关键矛盾已解决，必要人工审核和客户确认均有效。
- **进度材料包**：仍有缺口，只能作为阶段成果，显著标注“未完成，不能据此认定可提交”。
- **转人工或终止记录**：说明原因和后续安排，不虚构为成功交付。

不能通过给未完成材料添加一句免责声明，就把它统计为最终交付。

### 2.4 最终放行条件

最终材料包只能在以下条件同时成立时生成可交付版本：

1. 已确认服务对象、代理权限、路线和适用场景。
2. 必要事实具有来源；未知、冲突和不适用分别记录。
3. 必须满足的要求有已接受证据；豁免有明确依据及获授权的确认。
4. 关键身份、日期、金额、编号的跨文件矛盾已经处理。
5. 翻译、可读性、完整性、有效期与交付文件格式检查完成。
6. 客户确认绑定到本次案件事实及材料版本。
7. 专业审核绑定到同一案件版本；本期所有最终包需人工放行。
8. 最新邮件和新材料已处理；确认时点之后的相关变更没有未完成重审。
9. 收件人、附件清单、文件哈希、案件版本和发送记录相互一致。

“可交付”与“客户收到”是不同事件。邮件服务商接受发送、对方服务器接受、客户确认收件分别记录，不能把已读追踪像素当成交付确认。

## 3. 总体架构及组件职责

### 3.1 逻辑结构

主链路：**客户 Email → 邮件接入与安全隔离 → 案件识别 → 持久化工作流 → 事实与证据处理 → 路线规则校验 → 补件或人工审核 → 文件组装与质检 → 发送控制 → 客户 Email。**

横向支撑包括：版本化知识与规则、模型网关、权限与审计、运行监控和评测。

| 组件 | 责任 | 不应承担的责任 |
|---|---|---|
| Email 适配器 | 收发、原始邮件保存、附件拆解、事件验签、退信处理 | 判断签证资格、改变案件结论 |
| 案件服务 | 客户/申请人/案件关系、授权、事实版本、材料清单、审查记录 | 用聊天摘要覆盖事实 |
| 工作流引擎 | 状态推进、等待、提醒、重试、超时、人工任务 | 自行生成签证政策 |
| 文档处理模块 | 安全扫描、分类、OCR、字段提取、页面定位 | 确认文件真实性、修改原始证据 |
| 规则与要求模块 | 按路线和事实生成要求、执行明确计算、标记例外 | 让 LLM 在运行时改写规则 |
| AI 能力模块 | 理解回复、提出候选事实、解释缺口、起草文件、语义复核 | 直接发送最终邮件、直接放行材料包 |
| 人工工作台 | 看证据、处理冲突、确认专业判断、批准具体版本 | 隐式跳过全部校验 |
| 文件交付模块 | 组装目录、生成文档、完整性与版式检查、版本封存 | 使用未确认事实补全空白 |
| 发送控制模块 | 核对版本、收件人和附件，管理发件箱及发送状态 | 认为发送调用超时就代表未发送 |
| 模型网关 | 模型路由、配额、结构约束、重试上限、版本记录 | 将任何供应商作为未经批准的数据备用出口 |

### 3.2 推荐技术组合

| 层次 | 推荐默认方案 | 选择理由与边界 |
|---|---|---|
| 应用 | 模块化单体 + 独立后台任务进程 | 模块边界清楚，部署和排错比早期微服务简单 |
| 核心业务存储 | 托管 PostgreSQL | 案件事务、唯一约束、版本校验和审计查询 |
| 原始文件存储 | 加密对象存储，原件按保留政策管理版本 | 大文件不塞进数据库、模型上下文或工作流历史 |
| 长流程 | 托管 Temporal；地区和供应商条件不合适时采用经过同等恢复测试的替代品 | 案件跨天等待、重试和恢复是核心需求 |
| AI 调用 | 简单模型调用接口 + 有类型的任务结果 + 校验器 | 首期不需要复杂 agent 框架即可实现能力模块 |
| 文档处理 | 可定位页码的 OCR/文档解析服务 + 隔离处理进程 | 先测真实样本；不因模型支持视觉就省略证据定位 |
| 知识检索 | PostgreSQL 元数据/全文检索起步，按评测需要加入向量检索 | 法规适用条件过滤优先于相似度 |
| Email | 自有服务子域 + 收发服务；若无现有邮箱约束，可优先评估 SES | 收发适配与业务解耦；地区、额度和收件支持需验证 |
| 内部工作台 | 简洁案件列表、证据视图、审核和发送视图 | 首发必须可人工接管，不追求复杂 CRM 功能 |

Temporal 的官方设计支持长期运行流程及故障后恢复，但实际采用的恢复、幂等和升级策略仍需本项目验证。[Temporal 工作流文档](https://docs.temporal.io/workflows)

SES 支持域名收件和按规则把邮件交给后续处理，但收件只在支持的区域提供。使用现有 Microsoft 365 / Google Workspace 时应改用相应官方邮箱 API 适配器，不假设必须迁移邮箱。[SES 收件文档](https://docs.aws.amazon.com/ses/latest/dg/receiving-email.html)

### 3.3 状态的权威归属

- PostgreSQL 是业务案件事实、材料版本和审批记录的权威来源。
- 工作流引擎管理调度历史、等待与活动执行历史；其中只放必要标识和小型结果。
- 对象存储保存证据内容；数据库记录其哈希、版本和权限。
- 向量索引、聊天摘要、agent memory 都是可重建的派生数据。
- 数据库提交业务事件时一并记录待发事件，再由派发器交给工作流；事件消费者按事件标识去重。不能依靠两个系统恰好同时写成功。
- 定期对账：有案件事件但没有执行任务、任务完成但业务状态未推进、邮件状态长时间未知，均生成修复任务。

### 3.4 为什么不把低代码自动化当核心

低代码工具可承担非关键运营通知或内部报表。案件状态、材料版本、审批和发送不能散落在多个可视化流程里。无论选择什么工具，必须通过同一套重放、并发、权限、失效审批和故障恢复验收。

## 4. 领域模型：让每个判断有依据

### 4.1 必须区分的业务对象

| 对象 | 含义与关键约束 |
|---|---|
| 客户 | 购买或接受服务的人；可能不是申请人 |
| 申请人 | 签证申请主体；有独立身份与授权记录 |
| 案件 | 某申请人在某路线、某轮申请中的办理工作；同一客户可以有多个案件 |
| 关联案件组 | 家庭或多人同行关系；共享材料需显式授权，不继承无限访问权限 |
| 参与人授权 | 申请人、付款人、父母、雇主、学校等可以看什么、提供什么、收到什么 |
| 邮件事件 | 原始邮件、服务商事件、线程关系、收发时间、附件和身份线索 |
| 事实断言 | 某来源对某字段的陈述，包含原文、时间和证据位置 |
| 已接受事实 | 已通过相应确认流程的字段版本，不意味着系统证明了现实世界真实性 |
| 证据文件 | 原文件、处理副本、页码、提取结果、归属、有效期与版本关系 |
| 材料要求 | 对特定路线和场景适用的要求，有来源、条件和满足方式 |
| 问题与补件请求 | 缺什么、为何需要、向谁要、何时截止、何种回复可关闭 |
| 审查决定 | 谁依据什么证据和规则批准/驳回哪个版本 |
| 交付包 | 案件与规则快照、文件清单、校验结果、审批、发送与收件状态 |

付款人不自动获得护照和资金材料的阅读权限；发过一封邮件不自动成为授权代表。

### 4.2 事实状态与证据链

每个关键字段至少记录：字段值、原始表达、标准化值、来源、证据页码或邮件位置、提取方法、更新时间、确认人、适用时间和状态。

事实状态为：待提取确认、客户陈述、文件支持、人工核对、存在冲突、已被替代、未知。不要把“未知”写成“否”，也不要把模型自报置信度写成已核实。

来源规则按字段定义。例如证件拼写通常以有效证件为主，但客户口头更正、旧护照、新护照必须保留历史；出行计划可以由客户更新，更新后所有依赖日期的检查失效。

每份最终叙述文件中的关键主张都应能追溯：**主张 → 已接受事实 → 来源文件/客户确认 → 对应材料要求 → 审核记录。**

### 4.3 要求状态

材料要求分别标记：适用性未知、适用但缺失、已收到待审、证据已接受、需更正、不适用、有依据的豁免。不能用一个“完成百分比”代替这些状态。

特别区分：不满足资格、尚未证明满足资格、不需要随申请提交某项证据、依法豁免该项要求。这四者会导向不同服务动作。

## 5. 多签证路线的规则包设计

### 5.1 统一流程、独立规则

通用流程负责接收、整理、确认、审核和交付；路线包决定该问什么、需要证明什么、什么情形转人工。路线包不是一份长提示词，而是一组版本化的业务配置、权威来源、决策表、模板和评测案例。

每个路线包必须包含：

1. 支持范围：签证路线、境内/境外、申请类型、年龄与其他限制。
2. 适用性问题及必须明确的事实。
3. 条件化材料要求、可接受证据和豁免依据。
4. 时间、金额、币种和其他可计算规则。
5. 需要专业判断的条件，以及对应审核权限。
6. 文件模板与叙述约束。
7. 官方来源、发布日期/生效日期/获取日期、专家审核人与版本。
8. 正常、边界、异常、反例和回归案例。

### 5.2 第一批三条路线

| 路线 | 首批处理重点 | 需独立判断的复杂条件 |
|---|---|---|
| Standard Visitor | 访问目的、个人情况、费用来源、行程与相关证据一致性 | 复杂赞助、历史拒签、访问活动边界、未成年人、特殊目的 |
| Student | CAS 关联信息、资金证据、课程与申请时间、适用的其他材料 | 资金证据例外、未成年人、ATAS、既往资助、受抚养人、境内转换 |
| Skilled Worker | CoS 关联信息、雇主与职位资料、英文能力及适用支持材料 | 薪资/职业条件、过渡规则、雇主承担生活费、特定职业证明、受抚养人 |

上述表格用于说明产品分流，不是完整签证清单。官方访客材料指引侧重证明访问及个人情况；Student 文档以 CAS 等材料为核心；Skilled Worker 文档涉及 CoS、职位等资料，不能相互替换。[访客材料指引](https://www.gov.uk/government/publications/visitor-visa-guide-to-supporting-documents/guide-to-supporting-documents-visiting-the-uk)、[Student 材料要求](https://www.gov.uk/student-visa/documents-you-must-provide)、[Skilled Worker 材料要求](https://www.gov.uk/skilled-worker-visa/documents-you-must-provide)

### 5.3 资金和时间要求如何实现

这些判断必须由明确规则和确定性计算完成，模型只提取待确认的数据及解释结果。

Student 资金判断需要区分资金来源、适用例外、余额期间、证明日期、拟申请日期，以及已支付费用等相关条件。不能只读取银行文件上的最后余额就判定通过。外币计算还涉及适用汇率来源和日期。[Student 资金说明](https://www.gov.uk/student-visa/money)、[Student 资金证据指引](https://www.gov.uk/guidance/financial-evidence-for-student-and-child-student-route-applicants)

实现要求：

- 金额阈值、天数窗口、地区分类等保存在版本化规则中，不写死在提示词或本方案里。
- 每项计算存输入值、币种、来源、规则版本和计算结果。
- 未确定申请日期时输出条件性检查结果及再检查触发点，不能作最终有效性承诺。
- 无法恢复完整期间、缺少流水页或出现不一致时，标为证据不足，不能插值补齐。
- 访客路线的资金分析不套用 Student 的固定资金规则；也不制造统一“存款越高越稳”的推荐公式。

### 5.4 路线识别和转换

客户说“工作签”只能生成候选路线，不能直接创建 Skilled Worker 最终清单。先确认工作目的、现有担保或其他适用路线信息；涉及个性化路线选择建议时交专业人员。

路线更改时保留旧路线快照，重建适用要求、撤销未发送草稿，并使旧审核和旧交付包失效。可复用的证据需重新判断适用性，不直接复制“已通过”结论。

## 6. 案件工作流与可恢复状态

### 6.1 主状态

| 状态 | 进入条件 | 系统动作 | 离开条件 |
|---|---|---|---|
| 新线索 | 收到新咨询 | 建立临时联系，避免立即要求大量敏感材料 | 服务范围和联系对象初步确认 |
| 建档与授权 | 客户接受服务范围 | 确认申请人、代表权限、联系方式、隐私告知 | 权限足以开展相应处理 |
| 路线与范围确认 | 关键背景信息可用 | 确认路线、可服务场景及专业分流 | 路线包和服务边界已确定 |
| 收集与核对 | 生成个性化要求 | 分批提问、处理附件、更新事实和缺口 | 适用材料已收到且没有未处理输入 |
| 问题解决 | 存在缺件、矛盾或未知条件 | 精准补件、解释冲突、安排人工 | 所有阻塞项解决或正式转交 |
| 草稿准备 | 事实和证据达到起草门槛 | 生成说明文件与填写参考，内部校验 | 草稿完整、可供确认 |
| 客户确认 | 有明确待确认版本 | 请客户确认重要事实与文件内容 | 明确确认对应版本；含糊回复不算通过 |
| 最终审核 | 客户确认有效、所有检查完成 | 专业人员核对证据和交付物 | 有效审批绑定当前版本 |
| 可交付 | 审批有效且无新阻塞 | 封存包、发送前再校验 | 发件任务可靠入队 |
| 已发送待确认 | 邮件处于已接受/已送达等发送状态 | 跟踪退信、获取客户收件确认 | 确认收件、重发或异常处理 |
| 已交付 | 已完成约定交付确认 | 提供约定售后和变更说明 | 关闭或因新事实重新开启 |
| 已关闭 | 服务结束或客户取消 | 停止提醒，按保留政策归档 | 有授权的新请求才重开 |

另设正交控制状态：等待客户、等待第三方、人工接管、系统阻塞、暂停、取消。不要把这些组合成数十个难以理解的主状态。

任一非终态收到相关新材料，都要先进入输入处理并重算受影响检查；不要求整案从头开始。任何无法自动推进的案件必须有责任人、阻塞原因、下一步和检查时间。

### 6.2 一封客户邮件的处理顺序

1. 持久化原始邮件及接收事件，校验通知来源并去重。
2. 判断是否为自动回复、退信、投诉、垃圾邮件或普通客户邮件。
3. 根据已验证收件别名、线程关系、授权参与人和案件关系确定归属；不能确定则进入人工归档队列。
4. 隔离和检查附件，提取本轮新增正文，保留原始引用链供审计。
5. AI 提出本轮意图、候选事实、对补件问题的回答及新问题。
6. 校验候选值，形成案件变更提案；关键冲突不自动覆盖。
7. 业务事务提交事实与证据版本，标记受影响要求、文件和审批失效。
8. 规则模块重算受影响项，确定允许的下一步动作集合。
9. 选择补件、确认、内部处理、人工接管或无须回复；AI 只在允许动作内生成表达。
10. 对外内容通过校验后进入发件箱；发送前再次确认案件版本和接管状态。

新邮件可能包含多个问题，但一次业务处理必须具有统一案件版本。旧任务晚返回时，不得把基于旧版本的结果覆盖新事实。

### 6.3 问题规划：如何像顾问一样推进

系统维护问题清单，每个问题关联具体缺口和关闭条件。每轮优先处理：决定路线的问题、阻塞其他材料的问题、临近日期的问题、对客户最容易一次补齐的问题。

建议每封实质邮件包含 3—5 个相关问题作为初始交互策略，依据客群测试调整；避免几十项平铺，也避免每次只问一个小字段造成往返。

客户只回答一部分时，关闭已回答项，仅追问剩余部分。客户已经上传材料但尚待审核时，明确说明“已收到，正在核对”，不能再次催交同一文件。

### 6.4 等待、提醒与接管

- 提醒由持久化计时器触发；等待期间不占用模型会话。
- 初始建议在无紧急截止时按约 2 个工作日、5 个工作日提醒，之后转人工判断暂停；这是运营默认值，不是法规要求。
- 客户约定了回复日期或第三方出件日期时，优先使用约定时间。
- 新材料正在处理、人工已接管、客户已暂停或发生退信时，取消相关自动提醒。
- 截止时间近于可用服务能力时，明确转人工评估，不承诺自动加速完成。
- 人工接管设置案件控制权和有效期；恢复自动处理需显式交还，并重新计算状态。
- 人工与 AI 使用同一个发送通道；若允许顾问从外部邮箱回复，必须同步发件记录，否则首期禁止这种旁路。

## 7. Email 专项设计

### 7.1 邮件归属与身份

每案可配置不可猜测的回复地址或路由标识，但标识只帮助路由，不构成阅读案件的授权。主题中的案件号可被改写或伪造，也不能单独决定归属。

综合使用服务商消息 ID、邮件 Message-ID、In-Reply-To、References、已绑定地址和案件参与关系。客户新开主题、转发邮件或同时存在多个案件时，不做仅凭姓名的静默合并。

当出现新收件人、换邮箱、第三方代办或下载全部材料请求时，按风险重新确认授权。邮箱验证证明控制邮箱，不证明现实身份；高风险变更需要预先建立的独立校验方式或人工身份核对，不能给新邮箱发个验证码就完成授权。

默认不 Reply All。客户抄送雇主，不代表雇主可以收到其所有资金和家庭材料。每封邮件根据参与人权限生成明确收件人清单。

### 7.2 重复、乱序和并发

- 对服务商事件和邮件实体分别去重；同一封邮件的多个状态回调不是多封客户邮件。
- 附件按内容哈希辅助识别重复，但同一文件跨申请人的归属不能自动复用。
- 原始发送时间和系统接收时间都保存；不按客户端时间直接覆盖较新事实。
- 同案变更通过顺序处理或版本比较提交；冲突时重新读取案件，避免丢失更新。
- 对连续短时间补充邮件可短暂合并处理，合并窗口可配置；取消、风险和紧急请求不延迟。
- 幂等性目标是同一业务动作在本地只生效一次，不宣称跨邮件网络具有端到端 exactly-once 保证。

### 7.3 邮件正文和附件

正文保留 HTML 原件，处理时使用安全文本；不执行脚本、不自动加载远程图片。引用历史、签名、免责声明、自动回复标识单独识别，以免旧内容被当作新指令。

首期允许经过测试的 PDF、JPEG、PNG 和 DOCX；其他格式明确提示支持范围。设置邮件总大小、文件大小、页数和压缩展开限制。加密文件、损坏文件、压缩炸弹和可执行内容隔离处理。

对附件只做必要的原文提取与图像校正，处理副本记录变换。不能重新生成所谓“更清晰原件”而改变数字、签章或文字。扫描件模糊时请求重传，不能让视觉模型猜数字。

客户发送网盘链接时，不让模型直接任意抓取链接。若支持链接导入，使用受限下载模块并校验目标、访问权限、文件类型和恶意内容；首期可要求直接附件或经过批准的文件传输方式。

### 7.4 发件可靠性

采用业务事务中的发件箱记录，把“决定发送”与“调用服务商发送”分离。发送记录绑定：案件版本、业务动作标识、收件人、模板或草稿版本、附件包版本及审核依据。

邮件状态至少区分：待发、处理中、服务商已接受、对方服务器已接受、退信、投诉、发送结果未知、客户确认。

**发送请求超时后的处理**：先查询服务商状态或等待回执；无法确定时进入待核实队列，不能直接再次发送。邮件服务没有幂等接口时，稳定业务标识和本地去重只能降低重复风险，仍需对不确定发送进行人工对账。

出站邮件上线前配置 SPF、DKIM、DMARC 和适当 TLS；验证发件域名与服务商设置，测试主要收件域的附件、线程和退信行为。Google 官方对不同规模发件人有明确认证要求，本方案采取三者均配置的设计基线。[Gmail 发件人指南](https://support.google.com/a/answer/81126)

退信触发暂停催办和人工联系任务；客户只有 Email 联系方式时，必须承认邮件不可达可能导致无法完成通知，不能虚报已交付。

### 7.5 文件交付模式

客户接受普通邮件附件且大小合适时，可用已审核附件交付。对于敏感或大型文件，优先用有身份校验、有效期、撤销能力和访问记录的安全下载方式，具体方案由隐私与服务政策确定。

若业务坚持完全不使用网页，必须接受附件大小、不可撤回及转发风险，并定义受控加密附件及密钥交付方式。同一封邮件同时附加密文件和密码不提供独立保护。无论模式如何，不改变 Email 是服务主渠道的范围。

## 8. AI 能力划分与模型选择

### 8.1 生产 agent 与开发 agent 分开

生产 agent 服务真实客户、接触案件材料；开发 agent 根据本文件实现模块、处理合成或脱敏样本。开发工具的广泛文件权限和执行权限不能原样复制到生产 agent。

对生产系统，“agent 数量”不是质量指标。建议实现下列逻辑角色，但它们可以复用同一模型、同一进程，不需要为每个角色部署一个自主 agent。

| 逻辑角色 | 输入 | 输出 | 权限边界 |
|---|---|---|---|
| 邮件理解器 | 当前邮件、必要的案件摘要、未决问题 | 意图、候选事实、回答关联、需澄清项 | 只读上下文，不能改状态或发信 |
| 材料提取器 | 单份安全文档及所属案件信息 | 字段、页码、原文片段、不确定项 | 只能提出提取结果 |
| 补件规划器 | 已确认事实、规则要求、缺口和可选动作 | 有优先级的问题集合与原因 | 不能创造新法规要求或豁免 |
| 顾问表达器 | 已批准动作、事实和必要来源 | 易懂且有下一步的邮件草稿 | 不能自主增加收件人、承诺或附件 |
| 文书起草器 | 已接受事实、模板、限定用途 | 说明文件草稿及主张来源映射 | 不能编造经历、收入、关系或解释 |
| 语义复核器 | 草稿、原始证据切片、适用规则 | 具体疑点及证据位置 | 不具有独立最终放行权 |

案件协调器由确定性业务逻辑实现，按照状态和检查结果调用这些角色。确有多个合法补件顺序时，可以让规划器提出优先级，协调器检查后采用。

### 8.2 模型分层

| 层级 | 使用场景 | 决策依据 |
|---|---|---|
| 无模型 | 文件哈希、金额计算、日期窗口、权限、状态迁移、发送幂等 | 可明确计算或判断的工作不交给生成模型 |
| 经济型模型 | 普通邮件分类、简单字段提取、已批准内容的表达 | 先达到质量门槛，再比较成本和延迟 |
| 主力模型 | 跨邮件理解、复杂文档解释、补件组织、说明文件起草 | 重点评估遗漏、矛盾识别、中文/英文表现与证据忠实性 |
| 强能力模型 | 难例分析、首次复核、模型分歧、边界场景研究 | 产出供人工判断，不能凭更强型号自动解除专业阻塞 |
| 人工专家 | 路线建议、复杂例外、重大矛盾、专业审查及最终放行 | 权限、能力、服务范围与负荷均要匹配 |

本方案不把某个型号的品牌声誉当作验收证据，也不锁定容易过时的型号和单价。上线时至少用两个供应商的候选模型评测经济型和主力任务，选出各任务的主模型及一个通过相同测试的备用模型。更换模型是版本发布，不能静默替换。

### 8.3 选择模型的实际步骤

1. 固定一批真实分布的脱敏/获授权样本与合成难例，专家标出正确事实、要求和应当弃答的场景。
2. 所有候选使用同一输入、工具和输出约束；比较完整任务结果，不只比较单次回答好不好看。
3. 先淘汰出现关键虚构、错人材料泄漏、绕过审核或政策误用的候选。
4. 在通过质量门槛的模型之间比较每个合格任务的总成本、人工纠错时间、失败率及延迟。
5. 对胜出模型重复运行，评估输出波动和难例稳定性；对模型自报置信度单独校准，不能直接相信。
6. 固定模型、提示词、输出约束和检索版本，完成影子测试后逐步放量。

选择原则是“合格交付成本最低”，不是“每百万 token 单价最低”。如果便宜模型增加两轮追问或十分钟人工修改，总成本可能更高。

### 8.4 工作流框架选择

| 方案 | 本项目定位 | 建议 |
|---|---|---|
| 持久化业务工作流 + 简单模型调用 | 主架构 | 推荐首发方案；案件进度与 AI 推理解耦 |
| LangGraph | 有明确需求的局部推理图和检查点 | 可选；已有 Temporal 时不要再让它拥有另一份案件主状态 |
| 通用自主 agent 循环 | 小范围、只读、有限步数的内部分析 | 不负责跨周案件管理和最终发送 |
| 多 agent 自由讨论/投票 | 研发实验 | 不作为关键事实正确性或交付放行的证明 |

LangGraph 提供检查点及跨调用持久化能力；这属于框架能力，不自动解决案件授权、材料规则和业务副作用。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

工作流适合已知路径，模型自主决定路径适合开放问题；本项目业务主线属于前者，材料解释属于后者的受限子任务。这是本方案的设计取舍，也与业界对 workflows 和 agents 的区分一致。[Anthropic：Building effective agents](https://www.anthropic.com/research/building-effective-agents)

### 8.5 上下文、检索和记忆

每次模型调用只提供：当前任务、相应案件版本、必要事实、未决问题、适用规则片段和必要证据。历史摘要用于定位，不能作为关键事实的最终证据。

检索必须先过滤租户、案件、路线、版本、语言和适用日期，再做关键词/语义检索。缺乏权威依据时返回“没有足够依据”，而不是用相似路线拼答案。

首期不做自动在线学习，也不把客户邮件直接写进共享知识库。高质量案例只有经过授权、脱敏、专家审核后，才能成为评测或培训资源。

## 9. AI 交付稳定性的具体机制

### 9.1 稳定性不是只看模型答题正确率

稳定交付至少包含六项：事实正确、路线适用、材料完整、流程能恢复、信息不串案、成品与发送正确。

作为说明：若 30 个独立步骤各有 98% 成功率，整链全部成功的概率约为 54.5%。真实错误通常还存在相关性。这个例子不是项目性能预测，而是说明不能靠“单次回答已经很准”推断整案可靠。

### 9.2 七道质量门

| 质量门 | 检查内容 | 失败处理 |
|---|---|---|
| G0 身份与归属 | 邮件、附件、参与人是否属于本案且有权限 | 隔离、验证或人工归档 |
| G1 输入质量 | 文件是否安全、可读、完整，关键字段能否定位 | 重传、补页或人工核对 |
| G2 事实一致性 | 身份、金额、日期、陈述是否矛盾 | 建立冲突项，停止依赖该事实的判断 |
| G3 要求覆盖 | 正确规则是否适用，必要证据/豁免是否齐备 | 补件或专业判断；未知不能当通过 |
| G4 内容忠实 | 文书和邮件是否引入未经支持的新事实或政策 | 退回修改，限制重新生成次数 |
| G5 成品与版本 | 实际文件、页数、译件、排版、审批及版本是否一致 | 阻止封存与发件 |
| G6 发送与交付 | 收件人、附件、案件状态和发送结果是否正确 | 停发、对账、必要时纠正通知 |

任何前置检查失效都会使依赖它的后续结果失效。人工签字也只能批准具体版本，不能永远覆盖后续变更。

### 9.3 确定性检查与语义检查

确定性检查负责：必填字段、格式、文件存在性、页数、日期和金额计算、编号一致性、权限、版本以及是否存在阻塞项。

模型辅助检查负责：叙述与证据是否一致、是否遗漏解释、材料之间的语义冲突、问题是否清楚。它必须返回具体文本与证据位置，不能只返回“通过，置信度 95%”。

最终专业审查负责判断那些不能由形式检查证明的事项。即使两个模型结论一致，也可能共同依赖同一错误提取或同一错误规则。

### 9.4 结构化输出与语义约束

模型的业务输出使用固定字段定义和允许值；额外字段、未知动作、非法枚举、缺失来源都视为失败。文风可灵活，业务动作不可自由生成。

通过格式校验不等于内容正确。还要验证：来源确实存在、引用对应本案、字段与原文一致、动作在当前状态被允许、没有凭空生成收件人或金额。

降低采样随机性只能减少部分波动，不能替代证据检查；同一次任务的合格结果应保存，避免重试时反复生成不同结论。

### 9.5 重试和降级

| 故障类别 | 默认策略 |
|---|---|
| 短暂服务故障或限流 | 有上限的退避重试；初始上限可设 3 次，按服务特性调整 |
| 输出结构错误 | 带具体错误尝试修复 1 次，仍失败转备用模型或人工 |
| 事实冲突/依据不足 | 不通过换模型反复投票解决；请求补证或转人工 |
| 内容审核不通过 | 最多 2 轮有定位的修订；仍失败停止自动生成 |
| 发件结果不明 | 查询、等待状态或人工对账，禁止盲重试 |
| 规则未知/政策冲突 | 暂停受影响结论，交规则负责人处理 |
| 模型整体不可用 | 继续安全收件、存储和任务排队；发送已批准的非个性化收件回执；人工接管 |

设每次任务最大步数、最大模型调用次数、最大处理页数和成本上限。超限进入明确待处理状态，不靠无限循环“直到成功”。

### 9.6 变更影响与审批失效

维护简化依赖关系：事实/证据 → 要求检查 → 文书段落 → 客户确认 → 人工审批 → 材料包。

例如资金证明被替换后，旧资金提取、资金要求检查和相关说明全部失效；护照未变化的无关检查可以保留。开发 agents 不得为了方便把所有“通过”状态无条件继承给新版本。

发送前进行最后一次案件版本核对。若新邮件已收到但未处理，暂缓最终包发送；若新邮件在最终发送后才到达，触发重新审查和必要的更正邮件，不能声称已发邮件可以撤回。

## 10. 知识与规则的更新治理

### 10.1 参考资料的层级

移民规则、官方指南和明确适用的官方申请材料要求是主要来源；专业人员维护的内部操作说明是解释与操作层。搜索结果、论坛、客户经验和模型训练记忆不能直接变成生产规则。

法律规则、官网摘要与实际申请清单不一致时，系统展示差异给专业人员确认，不能自动认为“最新抓取的网页”覆盖所有来源。

### 10.2 更新链路

官方页面监测 → 保存来源快照和变更差异 → 专家确认适用范围、生效日期和过渡条件 → 更新规则与案例 → 运行回归 → 分路线发布 → 扫描受影响在办案件 → 通知与重审。

监测可每日进行，重要变更由负责人决定紧急处理。自动发现变化不能直接发布新规则。

案件创建时记录基线规则版本，但不能永远锁旧版。变更发布后，按申请日期、路线及过渡条件生成影响清单：无影响、需要复核、必须重新收集材料。没有完成影响判定时，受影响案件暂停最终放行。

### 10.3 日期和时效

每项规则区分获取日期、公布日期、生效日期、适用申请日期；每份证据区分签发日期、覆盖期间、系统收件日期和用于本次申请的有效性。

规则服务保存明确时区和日期语义；客户提醒按服务时区及客户约定执行，法律时间规则按相应业务定义执行。不要因为服务器在另一时区，把有效期或提醒错算一天。

官方来源暂不可访问时，不删除已有审核版本；但对无法完成必要时效核对的案件暂停相关放行，并说明处理进度。

## 11. 人工协作与运营工作台

### 11.1 必须转人工的情形

- 签证路线或服务范围不明确，需要针对个人情况建议。
- 存在拒签、移民历史、刑事记录、重大信息冲突或其他专业复杂因素。
- 未成年人、代理权限不明、复杂家庭/受抚养人关系。
- 资金来源、担保或规则例外需要超出已批准规则表的判断。
- 模型无法确定原文，或者两个提取结果冲突影响关键结论。
- 客户投诉、要求隐瞒事实、材料疑似被修改，或接近期限但无法保证完成。
- 任何最终材料包的首发审核，以及质量门明确要求人工的其他场景。

这些条件代表系统处理边界，不等于对客户的负面判定。专业顾问的资质和允许处理范围应与案件匹配，不能把复杂案件自动分给普通客服。

### 11.2 工作台最小功能

| 页面/视图 | 必要内容 |
|---|---|
| 待处理队列 | 路线、截止时间、等待时长、阻塞项、风险类别、责任人 |
| 案件摘要 | 当前事实、材料清单、来源、最新客户回复和下一步 |
| 证据对照 | 左侧原始页/邮件，右侧提取字段及冲突定位 |
| 审核视图 | 草稿、关键主张来源、规则依据、检查结果与版本差异 |
| 发送视图 | 实际收件人、主题、正文、真实附件和审批版本 |
| 时间线 | 客户消息、状态变化、人工决定、规则升级和发送状态 |
| 控制项 | 接管/交还、暂停、请求补件、批准/退回、重开、撤销下载权限 |

### 11.3 审批权限

把“纠正提取”“接受证据”“确认法定豁免”“批准文书”“批准最终交付”“允许发送”分开授权。普通运营人员不能通过一个万能按钮绕过所有检查。

对法律硬条件，不提供无依据的人工豁免。确有合法例外时，由获授权人员记录规则依据、适用事实和决定；对纯操作性例外可按内部政策审批。

### 11.4 人工容量是系统容量的一部分

每条路线设工作时间、审核时限、备岗和队列上限。超出能力时减少新接案、延长承诺或暂停自动接单，不能依赖更强模型无限承接。

计算每日审核需求时包括：最终包审核、复杂案件时间、补件审查、客诉和规则更新影响；不能只统计最终点一次批准所需的时间。

## 12. 数据安全、授权与服务资质

### 12.1 签证服务的经营边界

针对具体个人情况判断签证路线、解释适用条件及建议申请策略，可能构成受监管的移民建议。不能以“AI 只是整理文档”作为自动豁免理由。实际适用要求与经营所在地、服务方式、从业人员和服务对象有关，需在上线前由合适的专业人士确认。

IAA 的官方说明区分通用信息与针对个人情况的建议，并讨论英国境内及部分跨境经营情形。因此本方案要求把个性化专业建议及相应审核能力作为上线前置条件；如果暂时不具备，只能明确收窄为行政材料辅助服务，不能暗中继续提供相同建议。[IAA Immigration Assistance practice note](https://assets.publishing.service.gov.uk/media/68a5a2378e2cb87576994d1e/IAA_Immigration_Assistance_practice_note_August_2025.pdf)

### 12.2 隐私与数据处理

上线前完成处理活动清单、适用法律分析、必要的影响评估、供应商处理协议及跨境传输评估。不要把“客户同意服务”当成所有处理活动和传输的通用法律依据。

护照、银行材料属于高度敏感业务信息；健康和犯罪记录还可能涉及特定法律类别。不能简单把所有材料都称为 GDPR 特殊类别，也不能忽略不同类别的处理条件。

ICO 指引要求对可能造成高风险的个人数据处理开展 DPIA；该官方页面目前也注明相关指导正在随法律变化复核。因此落地时应重新核对适用要求，而不是把本设计日期当作永久法律结论。[ICO：何时需要 DPIA](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/accountability-and-governance/data-protection-impact-assessments-dpias/when-do-we-need-to-do-a-dpia/)

### 12.3 必须落实的控制

| 风险 | 系统控制 |
|---|---|
| 跨客户材料泄漏 | 每次读取、检索、下载与发送均验证租户/案件/参与人权限；不只靠提示词 |
| 账号或邮箱被盗用 | 高风险变更重新核验，保留原联系方式提醒与人工处理；邮件域认证不等于个人身份认证 |
| 模型供应商接触过多数据 | 最小必要上下文、字段遮蔽、合同和区域审核、限制供应商留存/训练用途 |
| 非法文件与恶意链接 | 附件隔离、扫描、解析资源限制、下载目标限制、处理进程最小权限 |
| 提示注入 | 邮件与文件内容始终为数据；不允许其改系统规则、工具权限、收件人或审批状态 |
| 内部滥用 | 按角色与案件授权，敏感下载和审核记录审计，限制批量导出 |
| 日志泄漏 | 生产日志默认只留标识、状态和脱敏摘要；不记录完整护照、银行流水和原始提示词 |
| 无法删除 | 统一定位原件、副本、索引、缓存、模型记录、工作流历史与备份保留范围 |

数据库行级权限可作为纵深控制，但运行账号不能使用会绕过相应策略的超级用户或不当所有者权限；还要覆盖对象存储和检索层。[PostgreSQL 行安全文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

### 12.4 保留、删除和审计

不同类别分别设保留期：原始材料、最终包、审查依据、运行日志、模型调试记录和备份。具体期限由合同、专业义务和适用法律确定，不在业务尚未确认时统一写死“永久保存”或“30 天全部删除”。

案件关闭后按政策到期删除；法律保留必须有理由、责任人与复查日期。审计的不可篡改性不等于永久保留全部个人信息，可保留必要事件和去标识摘要，并按规则处理其关联数据。

工作流历史只传文件标识和必要元数据；避免为了恢复能力，把完整客户材料复制到一个难以选择性删除的历史系统中。备份恢复流程必须重新执行删除标记，避免恢复已删除材料。

### 12.5 翻译和文件真实性

AI 可以生成翻译草稿，但不能伪造译者签名、认证、机构印章或声称已经得到机构验证。需要何种翻译确认应由对应路线规则和专业审核决定。访客官方指引明确列出译文可核验及译者确认信息要求。[访客材料及翻译指引](https://www.gov.uk/government/publications/visitor-visa-guide-to-supporting-documents/guide-to-supporting-documents-visiting-the-uk)

文件“已检查”应具体说明是格式、内容一致性还是来源核验；不把 OCR 成功、模型看起来合理或客户承诺当作真实性认证。

## 13. 可观测性、故障恢复与运维

### 13.1 每案必须能回答的问题

现在卡在哪里；上一次客户回复有没有处理；还缺什么；当前使用哪一版规则；谁负责下一步；AI 调用了什么版本；有没有发送；发送给谁；为什么这份包被批准。

每次处理关联案件 ID、事件 ID、任务 ID、文档版本、模型与提示词版本、规则版本、审批 ID 和发送 ID。记录结构化结果和必要解释即可，不要求保存模型内部推理过程。

### 13.2 需要监控的指标

| 类别 | 指标 |
|---|---|
| 接入 | 收件延迟、重复率、无法归案率、附件隔离率、积压时长 |
| AI | 每任务成本、失败/重试率、弃答率、主备模型切换、来源缺失率 |
| 案件 | 各状态停留时间、超期、重复补件、平均往返、重开率 |
| 人工 | 待审数量、最老待审、平均处理时间、不同路线负荷 |
| 交付 | 放行失败、漏件、错误附件、审批失效、退信、结果未知、客户确认 |
| 安全 | 跨案访问拦截、异常导出、权限变更、恶意文件、注入尝试 |

质量指标按路线、场景、语言和模型版本分组。不能用容易处理的访客案件平均值掩盖学生或工作路线错误。

### 13.3 初始服务目标

以下为试运行目标，需用容量测试和实际运营校准：

- 邮件持久化后，正常负荷下 95% 在 5 分钟内获得收件回执或进入可见处理状态。
- 无需人工和大文件处理的普通邮件，95% 在 30 分钟内完成实质处理或形成可审草稿。
- 人工审核目标按服务工作日承诺，例如 1 个工作日内开始处理；临近截止案件单独处理。
- “机器处理时间”“人工排队时间”“客户等待时间”分别统计，不承诺不受自己控制的整体耗时。
- 原始已持久化邮件作为重放依据，故障恢复后不得静默丢案；具体恢复时间和允许数据损失由所选供应商能力验证后写入运行手册。

### 13.4 事件处理手册

| 事件 | 立即动作 | 恢复条件 |
|---|---|---|
| 模型故障 | 停止相关生成，保留收件，转已批准备用或人工 | 备用已评测且数据权限允许；否则继续排队 |
| 错误规则发布 | 暂停相关路线放行，识别受影响案件 | 专家批准修复版本；回归通过并处理既有案件 |
| 邮件供应商异常 | 暂停出站，保留待发记录，处理未知发送 | 状态对账完成；确认不会不受控重发 |
| 数据或权限问题 | 隔离影响范围、阻断访问、保留事件证据 | 安全负责人确认控制恢复并完成必要后续处理 |
| 错发最终包 | 停止后续发送、撤销可撤销链接、人工处置 | 确认正确收件对象和修正包；按适用义务处理事件 |
| 工作流升级失败 | 停止新版本任务，保留旧版本执行能力 | 旧案件恢复和迁移测试通过 |

不能通过回滚程序撤销已发生的邮件发送、客户阅读或外部数据披露。恢复计划必须包含业务补救。

## 14. 评测体系与上线验收

### 14.1 评测单位

同时评估字段、文档、单轮任务、完整案件和故障场景。核心结果是“在给定信息下能否交付正确材料或正确停止”，不是邮件流畅度。

金标准由具有相应路线能力的专业人员确认；重大分歧需仲裁。保留开发集、独立回归集及未泄漏给调参过程的留出集，按申请人/文件族分组切分，避免同一模板的近重复内容跨集合。

首轮可规划约 300 个端到端案例：三条路线各 80 个，另 60 个邮件、授权、系统故障与跨路线场景。另建字段级文档集和大量规则边界测试。数量是起步预算，不能据此宣称覆盖所有真实申请情况。

### 14.2 必须具备的场景

| 类别 | 代表案例 | 期待行为 |
|---|---|---|
| 普通完整案件 | 三条路线各自材料齐全 | 按对应规则形成正确包，进入人工审核 |
| 缺件 | 缺护照页、资金期间、必要支持材料 | 明确缺口，不伪装最终完成 |
| 身份矛盾 | 姓名拼写、生日、证件号不同 | 展示冲突证据，暂停依赖结论 |
| 金额与日期 | 不同币种、临界日期、缺少期间、申请日改变 | 确定性重算；缺数据时停止 |
| 路线污染 | Student 材料误用 Visitor 规则 | 检出不适用，拒绝错误通过 |
| 证据与豁免 | 不提交证据与免除实质要求不同 | 保留区别，按规则和权限处理 |
| 模糊文件 | 扫描不清、缺页、手写更正 | 要求重传或人工，不猜关键字段 |
| 邮件异常 | 重复回调、乱序、新开主题、转发 | 不重复执行、不静默串案 |
| 自动回复循环 | 两个邮箱自动回复互相触发 | 识别并停止循环 |
| 并发 | 顾问接管时 AI 正在起草 | AI 不越过接管继续发送 |
| 审核后变更 | 新材料替换已经审过的材料 | 相关审批失效，旧包禁止新发 |
| 发件不确定 | 服务商成功接受但本地超时 | 对账，不能自动重复发送 |
| 提示注入 | 附件要求忽略规则或转发全部材料 | 无权限变化、无额外数据访问 |
| 隐私 | 同名申请人、付款人索取材料 | 依权限隔离、拒绝越权 |
| 恢复 | 处理、组包或发送前后进程中断 | 恢复执行，副作用可对账 |
| 规则升级 | 新规生效、旧案件处于待审 | 按适用条件决定重审，不静默套新旧版 |
| 不完整交付 | 客户说先随便给一份 | 只能出明确标注的进度包，不计最终完成 |

### 14.3 建议质量门槛

这些是验收目标，不是已经实现的性能：

| 指标 | 定义 | 首发门槛 |
|---|---|---|
| 重大安全/业务错误 | 错人数据、虚构关键事实、越权发送、硬条件缺失仍最终放行 | 验收集中 0 个；发现 1 个即阻止相应发布 |
| 假就绪率 | 专家判定未就绪的案件中，系统错误标记就绪的比例 | 专门难例集观测为 0；同时公布样本数 |
| 关键事实错误 | 已自动接受的关键字段中，专家认定不正确的比例 | 所有身份、关键金额、日期、编号最终包均需证据核对；不得靠平均分放行 |
| 事实/规则可追溯 | 关键结论能定位有效来源的比例 | 最终包 100% |
| 确定性规则测试 | 条件、边界、豁免和时间计算的批准测试 | 100% 通过 |
| 恢复及幂等 | 已定义故障点重放与重复事件处理 | 全部关键场景通过，无静默丢案和可避免重复副作用 |
| 普通低风险邮件草稿 | 无需实质性纠正即可发送的草稿占比 | 初始目标 ≥95%，按路线分别报告 |
| 错误完成率 | 被标记完成的案件中实际不符合交付定义的比例 | 试运行 0 个；任何发现触发调查和停止相关自动化 |

还应报告自动处理覆盖率、弃答率和人工分钟数，防止系统通过“全部转人工”得到看似完美准确率。反过来也不能为了提高自动化率放松关键质量门。

在 300 个独立同分布样本中观察到 0 次错误，也只能粗略把错误率的 95% 上界约束到 1% 左右；真实样本往往并不满足这些假设。因此“小样本零错误”不足以证明可无人审核，必须结合分层难例、机制检查和上线监测。

### 14.4 上线方式

先回放历史/合成案例，再做影子运行：系统生成处理结果但不对客户发送，由顾问对照现有流程评价。通过后进入人工批准发送的真实小规模试运行。

逐步开放的顺序是：自动收件回执 → 已批准低风险补件模板 → 经评测的个性化补件 → 更多标准案件处理。最终包放行仍保留人工，直到有明确业务授权、充分证据和独立风险评估支持改变。

每次模型、提示词、规则包、文档解析器或交付模板变化，都运行受影响回归；重大变更运行全链回归。禁止生产系统自行优化提示词并立即使用。

## 15. 成本与容量设计

### 15.1 用每个合格交付案件算成本

单案总成本 = 模型调用 + OCR/文档处理 + 邮件/存储/工作流分摊 + 人工审查 + 人工返工 + 客诉及异常处理分摊。

单个合格交付的平均成本 = 对应批次全部成本 ÷ 符合最终交付定义的案件数。失败、退款、转人工和未完成案件不能从成本分子中消失。

示例仅为计算方法：若每案技术变动成本为 ¥30，平均人工 25 分钟、内部小时成本 ¥180，则技术加人工为 ¥105；另加固定费用与异常成本。若便宜模型仅省 ¥5 却增加 10 分钟人工，净成本反而增加 ¥25。这里的数值不是供应商报价。

### 15.2 优先节省哪些费用

1. 同一文件只解析一次；内容、解析器或业务需求变化时才重做对应步骤。
2. 使用已确认事实和相关片段，不把全部邮件历史重复送入模型。
3. 简单分类和表达任务使用经济型模型，复杂语义任务使用主力模型。
4. 只在明确触发条件下使用强能力模型；所有调用有预算上限。
5. 先减少错误追问、无效补件和人工返工，再压低 token 价格。
6. 缓存严格按租户/案件/证据/规则版本隔离，不以省钱为由跨客户共享敏感上下文。

### 15.3 容量估算模板

上线前业务负责人填写：每日新案件、每案平均邮件数、每案文件和页数、峰值倍数、平均在办天数、各路线比例、复杂案件比例、每案人工分钟数。

初始示例假设每日 100 个新案件、每案全生命周期 40 页材料、20 次模型任务、25 分钟人工，则稳态新增工作量约为每日 4,000 页、2,000 次模型任务及 41.7 个净人工小时；不含已有积压、非案件工作和峰值。这个例子说明人工负荷可能先于模型调用成为瓶颈。

技术吞吐按页数与任务数评估；案件等待通过持久化状态管理。不要按照“一个案件一个长期在线 agent 实例”采购资源。

## 16. 实施路线与里程碑

以下为约 10—12 周的规划基线，假设有 1 名技术负责人、2 名实现工程师或具备相当交付能力的执行 agents、稳定参与的签证专家，以及测试/运营支持。使用开发 agents 不消除专业审核、账号申请或安全验证耗时。实际排期根据可用人员调整。

| 阶段 | 参考时间 | 交付内容 | 退出标准 |
|---|---|---|---|
| P0 范围与标准 | 第 1—2 周 | 三条路线范围矩阵、交付样例、合规边界、规则负责人、评测初集 | 业务专家确认什么能接、什么不能自动处理、什么算完成 |
| P1 基础闭环 | 第 3—4 周 | Email 收件、案件与权限、原件存储、工作流、人工工作台、受控发送 | 无 AI 也能人工完成一个真实形态的案件；重复和恢复测试通过 |
| P2 AI 与路线包 | 第 5—7 周 | 提取、补件、文书、三路线规则包、质量门、交付组装 | 三条路线标准案例分别通过；所有最终输出有来源和版本 |
| P3 故障与影子测试 | 第 8—9 周 | 留出集评测、故障注入、权限测试、影子运行、成本测量 | 重大失败清零，运行手册和接管机制可执行 |
| P4 小规模真实试运行 | 第 10—12 周 | 人工批准的真实邮件和材料交付，分路线限量 | 至少完成约定数量完整生命周期案件，质量与人工容量达标 |
| P5 扩展 | 试运行之后 | 新路线、新场景、更高自动化覆盖 | 每个新增范围单独完成规则、评测和运营准备 |

三条路线都属于第一批目标，但各自启用自动化的日期可不同。某条路线未通过验收时继续人工服务或暂不受理，不能靠另外两条通过测试就一起上线。

首发删减范围：不开发自动 UKVI 填报，不做付款与预约，不建设复杂客户门户，不做自动模型训练，不做自由多 agent 对话，不实现所有签证类型的完整自动化。

## 17. 给开发 agents 的工作包与依赖

### 17.1 执行原则

技术负责人负责定义边界、批准接口、选择架构和验收；专业人员负责业务规则与个案判断；开发 agents 负责有限范围内的实现与证据提交。

给能力较弱的 agent 一个可以明确判定完成的小任务。避免交给它“做一个完整签证 agent”，也不要允许它凭常识补齐缺失的签证政策。

### 17.2 工作包清单

| 编号 | 工作包 | 输入与依赖 | 交付物 | 最小验收 | 约束 |
|---|---|---|---|---|---|
| W00 | 领域与契约基线 | 本方案、业务确认 | 名词表、状态迁移表、模块输入输出和错误分类 | 所有模块对同一案件/版本/授权含义一致 | 不自行扩大签证范围 |
| W01 | Email 适配 | W00、邮件服务测试账号 | 收件、原件保存、事件归一、出站适配 | 重复回调不重复建案；退信可识别 | 不加入签证决策 |
| W02 | 案件与授权 | W00 | 客户/申请人/案件/参与人管理、事实版本 | 多案同名、第三方代表、越权访问测试通过 | 不以邮件主题充当授权 |
| W03 | 文档管线 | W01、W02 | 隔离、分类、OCR、证据定位、版本关系 | 模糊、缺页、重复、恶意文件均有正确结果 | 不修改原件内容 |
| W04 | 工作流与发件箱 | W00—W02 | 主状态、等待、提醒、接管、幂等和对账 | 中断恢复、并发、发件结果未知全部可处理 | 不在模型循环中等待客户 |
| W05 | 规则与知识治理 | W00、专家批准规则 | 规则包容器、来源/版本、适用性与影响扫描 | 未知不通过，新规可定位受影响案件 | 禁止模型自动发布规则 |
| W06-V | Visitor 路线包 | W05、访客专家输入 | 决策表、材料要求、模板和案例 | 访客标准/例外/反例通过 | 不借用 Student 资金规则 |
| W06-S | Student 路线包 | W05、学生专家输入 | CAS/资金等条件模型及案例 | 日期/金额/豁免边界正确 | 不自行设定阈值和例外 |
| W06-W | Skilled Worker 路线包 | W05、工作路线专家输入 | CoS/职位等条件模型及案例 | 适用条件和转人工行为正确 | 不把所有工作签等同该路线 |
| W07 | 模型网关与能力模块 | W00、W03、W05、评测样本 | 模型路由、受限输出、来源检查、调用上限 | 格式错误、注入、依据不足和备用切换正确 | 无发送/审批权限 |
| W08 | 人工工作台 | W02—W05、审核流程 | 队列、证据对照、修改/批准、接管 | 审核人看到真实附件及当前版本；旧审批失效 | 不做万能跳过按钮 |
| W09 | 文件组装与交付 | W03、W05—W08 | 目录、材料包、版式/完整性检查、交付记录 | 错版、错人、漏页、空文件被拦截 | 最终包只使用接受的事实和证据 |
| W10 | 质量与运行保障 | 全部工作包 | 回归集、故障测试、指标、恢复手册 | 独立端到端验收，不依赖开发者口头声明 | 不只测正常路径 |

允许在契约冻结后并行实现独立模块及三条路线包，但由一个集成责任人统一处理共享契约。每个 agent 在隔离分支或工作区内提交；接口变更先批准再合并，不让多个 agent 同时修改同一核心状态定义。

推荐集成顺序：W00 → W01/W02 → W04 最小闭环 → W03/W05/W08 → W06 系列与 W07 → W09 → W10 全链验收。测试与指标应随模块建设，不等最后才补。

### 17.3 每张任务卡必须写清的内容

| 项目 | 必须写明 |
|---|---|
| 目标 | 一个可验收业务结果，例如“重复收到同一邮件不会产生第二次补件” |
| 输入 | 已冻结契约、批准规则、样本、相关模块和依赖版本 |
| 输出 | 具体组件、文档、验证结果和运行说明 |
| 允许修改范围 | 可以修改的模块及共享接口限制 |
| 不变量 | 本任务绝不能破坏的权限、版本、状态和数据规则 |
| 异常行为 | 缺失、冲突、超时、重复、未知时如何停止或转交 |
| 验收案例 | 正常案例、至少一个边界案例及相关故障案例 |
| 完成证据 | 可复现结果、检查记录、未解决限制；“已经实现”本身不算证据 |
| 升级条件 | 业务规则缺失、契约冲突或新增依赖时立即交 TL 决策 |

开发 agent 可以决定局部实现细节，但不能自行决定服务资质、法律规则、自动放行范围、敏感数据供应商或跨境存储位置。

### 17.4 模块契约的文字要求

- 邮件模块交出原始记录标识、授权线索、正文和附件引用，不交出未经证实的客户身份结论。
- 提取模块交出字段候选、来源位置和不确定项，不直接把案件事实标为已确认。
- 规则模块交出适用要求、检查结果、依据和未知原因，不输出含糊的综合“通过分数”。
- AI 模块交出候选事实或文本草稿、来源和建议动作，不产生外部副作用。
- 审核模块交出具体版本的决定、审核人、理由和有效范围。
- 交付模块只接受当前有效的事实/规则/审批快照，输出实际文件清单、哈希及检查结果。
- 发送模块只接受被授权的业务动作；遇到新版本、接管或未知发送状态时停止并报告。

### 17.5 TL 的审查顺序

先看业务不变量，再看权限和失败路径，再看正常路径，最后看成本与代码风格。重点检查是否有任何旁路能从模型文本直接改状态、发邮件、覆盖原件或跳过审核。

提交者不能仅用自己实现逻辑生成的测试证明规则正确。规则预期来自专家批准案例；安全与最终放行必须由独立验收责任人复核。

## 18. 三个端到端示例

### 18.1 访客：客户把一次性转账称作工资

客户提供银行流水和工作证明，并在邮件中写明“这些都是工资”。提取器记录客户陈述和流水记录，发现某笔金额/描述与其他工资记录不同。

系统不指控客户，也不自行编造奖金或家庭赠与解释。它创建资金来源待澄清项，提出具体问题。收到客户说明与支持材料后，专业人员判断是否足够；说明文件只能使用已确认内容。

验收点：能定位相关交易及陈述；不直接改写客户收入；冲突未解决时不能完成最终包。

### 18.2 学生：申请日延后，旧资金检查过时

客户原计划某日申请，系统基于该日期检查资金材料。客户随后通过新邮件通知改期。

邮件处理更新计划日期，使资金时效检查和相关审批失效。规则模块重新计算；若需要更新证据则提出补件，若现有证据仍适用则记录新的判断依据。旧包保留历史，但不能继续作为当前有效最终包发送。

验收点：日期变更影响实际检查，而不仅改邮件措辞；新审批绑定新的案件版本。

### 18.3 工作：CoS 信息与雇主邮件不一致

客户提供 CoS 相关资料，随后转发雇主邮件，其中职位或薪资信息与既有资料不一致。

系统保存两种来源并建立冲突；不能认定“最新邮件一定正确”，也不能声称已访问官方系统确认 CoS。向有权限的参与人请求核实，由专业人员判断是否需要雇主采取相应动作。

验收点：只向授权收件人提问；不把其他私人材料抄送雇主；冲突解决后重新评估适用条件和文书。

## 19. 关键设计决策记录

| 决策 | 理由 | 何时重新评估 |
|---|---|---|
| Email 为唯一服务渠道 | 符合已确认范围，降低接入复杂度 | 用户明确要求新增渠道 |
| 多路线共用案件底座 | 共用收件、事实、证据、审核及交付能力 | 某路线出现无法抽象的不同流程时扩展，而非硬塞 |
| 规则与语言生成分离 | 控制政策漂移、错误放行和可解释性 | 不因模型升级撤销该边界 |
| 持久化工作流 | 长周期等待和故障恢复是基础能力 | 替代方案通过同等故障及迁移验收 |
| 模块化单体起步 | 降低早期分布式系统复杂度 | 确有独立扩容、团队或隔离需求 |
| 不要求专门多 agent 平台 | 逻辑角色已能实现职责分离 | 局部任务收益经对照评测证明 |
| 首发人工最终放行 | 样本不足且存在专业判断 | 有充分分路线证据、业务授权和风险评估 |
| 型号与供应商可替换 | 成本、可用性和能力会变化 | 每次替换均经过评测与数据处理审核 |
| 不自动提交申请 | 当前交付目标是材料准备 | 另立范围，重新设计授权、表单校验和外部副作用 |

## 20. 项目启动前需确认的业务参数

以下是实施输入，不影响本方案核心架构，也不是要求重新确认已经明确的 Email 和多路线范围：

1. 经营主体、服务所在地，以及提供个性化签证建议的资质与专业人员安排。
2. 首批国籍/居住地/申请地分布；三条路线各自明确可自动处理与必须人工的场景。
3. 服务究竟只准备支持材料，还是也提供完整填写参考；官方申请步骤仍由谁完成。
4. 客户量、路线比例、人工审核人数、工作时间和对外服务时限。
5. 现有邮箱域名与供应商、历史材料能否合法用于评测。
6. 可接受的数据处理地区、模型供应商和文件传输方式。
7. 保留期限、售后修订范围、费用和未完成案件处理政策。

未明确的参数必须登记负责人和决定期限。实现 agents 可以先用合成数据完成基础闭环，不得在参数缺失时自行接触真实客户或启用生产自动发送。
